## Per-spec deep-dive

### P1C-LLM-01-OVERLAP-CLASSIFICATION (10 calls per case)

**What it does:** For each D-XX domain, classify each sub-domain as IN_SCOPE/OUT_OF_SCOPE/PARTIAL relative to the company's applicable regulations.

**Inputs received:**
- `case_id` ✅
- `domain_id`, `lane_id` ✅
- `applicable_regs` ✅ (2 / 4 / 5 regs depending on case)
- `company_facts` (name, sector, jurisdiction, scale, employees) ✅
- `layer0_subdomain_refs` (4 entries per D-XX) ✅ — each entry has `sub_domain_id`, `title`, `hso_hl`, `participating_regulations`, `pairs`

**Sample (case 1, D-01):**
```json
{
  "case_id": "case1-tinytask",
  "domain_id": "D-01",
  "applicable_regs": ["GDPR", "CRA"],
  "company_facts": {"name": "TinyTask Lda.", "sector": "Technology/Software", ...},
  "layer0_subdomain_refs": [
    {"sub_domain_id": "D-01.1", "title": "D-01.1 Data at Rest Encryption", "hso_hl": "...", "participating_regulations": ["GDPR","NIS2","CRA","DORA"], "pairs": [...]},
    ...
  ]
}
```

**Verdict: ✅ The LLM has everything it needs to classify each sub-domain.** The user prompt explicitly enumerates the 4 sub-domains of D-01 with their HSO (Hierarchical Security Objective) text, the regulations that converge on each one, and the cross-regulation pairs. The LLM can decide IN_SCOPE/OUT_OF_SCOPE/PARTIAL based on this.

**Possible improvement:** The company_facts includes `scale: MICRO` (case 1) but the sub-domain metadata doesn't have a "minimum scale" field. The LLM has to make a proportional decision without explicit guidance — could improve by adding `tier_requirements` to each sub-domain ref.

### P1B-LLM-01-INTERPRETATION (N calls per case, N = applicable_regs)

**What it does:** For each applicable regulation, interpret the company's situation against the regulation's clauses, using the tipo2 catalog.

**Inputs received (in our test):**
- `case_id` ✅
- `lane_id` (regulation code) ✅
- `applicable_regs` (just that 1 reg) ✅
- `company_facts` (name, sector, jurisdiction) ✅
- `layer0_catalog.tipo2` ⚠️ EMPTY in our test (in real run, populated by the catalog loader)
- `layer0_subdomain_refs` (5 sub-domains relevant to this reg) ✅

**Sample user prompt (case 1, GDPR):**
```json
{
  "case_id": "case1-tinytask",
  "lane_id": "GDPR",
  "applicable_regs": ["GDPR"],
  "company_facts": {"name": "TinyTask Lda.", "sector": "Technology/Software", "jurisdiction": "Portugal (EU)"},
  "layer0_catalog": {"tipo2": []},
  "layer0_subdomain_refs": [<5 sub-domain dicts with hso_hl, hso_per_reg, pairs, ...>]
}
```

**Verdict: ✅ Context is RICH (323-598K user bytes). The LLM has the company facts and 5 sub-domain refs with full metadata.** The only questionable field is `layer0_catalog.tipo2: []` — in our test we explicitly set this to empty, but in a real run the catalog loader should populate it with the tipo2 interpretations for the regulation. **Worth verifying in a real run.**

**Concern: Prompt size.** 323-598K is large. The invoker caps at 512K (CORR-049). For cases 2/3 with 4-5 regs, the per-call size is at the cap. If the tipo2 catalog were also populated, the prompt could exceed the cap and be truncated. **Watch out in production.**

### P1B-LLM-02-RATIONALE (N calls per case)

**What it does:** For each applicable regulation, provide a rationale (justification for the interpretation). **Supposed to consume the output of P1B-LLM-01.**

**Inputs received (in our test):**
- `case_id` ✅
- `lane_id` (regulation code) ✅
- `applicable_regs` (just that 1 reg) ✅

**Sample user prompt (case 1, GDPR):**
```json
{
  "case_id": "case1-tinytask",
  "lane_id": "GDPR",
  "applicable_regs": ["GDPR"]
}
```

**That's it. Total user prompt: 280-290 bytes.**

**Verdict: ❌ TOO THIN. The LLM has NO context about the company, NO previous interpretations to rationale, NO sub-domain metadata.** The LLM can only produce a generic GDPR rationale that doesn't reference the company. **This is a bug — or at least a serious design issue.**

**Expected inputs that are missing:**
- `company_facts` (so the LLM can reference the company)
- `interpretations` (the output of P1B-LLM-01 for the same regulation)
- `layer0_subdomain_refs` (so the LLM can reference specific sub-domains)

**This explains the test P1B-LLM-02 produce-thin-output in the run log.** The LLM is asked to rationale but has nothing to work with.

**Recommendation:** Contract CORR-070 to fix P1B-LLM-02 input wiring — pass the company_facts, the prior interpretations, and the relevant sub-domain refs.

## Cross-cutting observations

### What the system prompt does (uniform across all 5 specs)

Every spec gets the same AEGIS base system prompt (~15KB), which establishes:
- The role ("AEGIS Phase 1 regulatory analysis assistant")
- The non-negotiable constraints ("Regulatory Baseline is READ-ONLY", "do not invent article numbers")
- The 5 canonical LLM spec IDs
- Cross-references to the methodology

This is good design — the system prompt is consistent and authoritative, regardless of which spec the LLM is being called for.

### What the user prompt does (varies by spec)

The user prompt is the per-spec injection of context:
- **P1C-LLM-01** (MAP): 27K — full sub-domain metadata for one lane
- **P1B-LLM-01** (interpretation): 323-598K — full metadata + tipo2 catalog
- **P1B-LLM-02** (rationale): 280-290 — **almost empty** ⚠️
- **P1C-LLM-02** (compound): 2.5K — cross-domain activations
- **P1C-LLM-03** (synthesis): 3.4K — full context

### What the LLM does NOT receive (gaps)

1. **P1B-LLM-02 missing company context** — can't rationale without knowing the company
2. **P1B-LLM-02 missing previous interpretations** — can't rationale an interpretation it doesn't see
3. **P1C-LLM-02 `doc07b_profile` empty in test** — needs verification in real run
4. **No `architecture` or `stakeholders` or `business_goals`** in any prompt — the LLM works only from the regulatory baseline + company facts, not from the company's actual structure

### What the LLM receives (correctly)

- ✅ Always: `case_id`, `lane_id`, `applicable_regs` (canonical)
- ✅ Always: AEGIS base system prompt (READ-ONLY constraint, methodology)
- ✅ P1C-LLM-01: `company_facts` + `layer0_subdomain_refs` with full metadata
- ✅ P1B-LLM-01: `company_facts` + `layer0_subdomain_refs` + tipo2 catalog
- ✅ P1C-LLM-03: `aggregated_activations` + `doc07b_profile`

## Methodology

1. Used `PromptLoader.render(spec_id, inputs)` to generate each prompt without calling the LLM.
2. Built the same inputs that the `Phase1Executor` would build in production (per spec).
3. Saved each (system, user, inputs) tuple to `/tmp/payload_capture3/<case>/<spec>__<lane>.json`.
4. For 3 cases × 5 specs, generated 58 prompts total.
5. Analyzed the contents to identify gaps.

**No HTTP calls to MiniMax were made.** Only `PromptLoader.render()` (purely local prompt assembly).

## Recommendations

In priority order:

1. **CRITICAL: Fix P1B-LLM-02-RATIONALE input wiring.** Pass `company_facts`, the `interpretations` from P1B-LLM-01 (same regulation), and the `layer0_subdomain_refs`. Without this, the LLM rationale is generic and useless. New contract (CORR-070) recommended.

2. **MEDIUM: Verify P1C-LLM-02 `doc07b_profile` is populated in production.** In our test it was `{}` because we didn't have the full Track B profile. In a real run, the orchestrator's `reduce_synthesis` should pass it.

3. **MEDIUM: Add input cap protection for P1B-LLM-01.** At 323-598K user bytes, the prompt is at the 512K cap. If the tipo2 catalog is also large (in our test it was empty), the prompt could exceed the cap and be truncated. Consider filtering the catalog by `applicable_reg` to reduce size.

4. **LOW: Consider adding `architecture` and `business_goals` to the user prompt of P1C-LLM-03.** The LLM does strategic synthesis but doesn't see the company's own organisational structure or goals. The strategic implications might be more grounded if it did.

5. **LOW: Consider adding `tier_requirements` to sub-domain refs.** The LLM does IN_SCOPE/OUT_OF_SCOPE/PARTIAL classification but has no explicit guidance on what scale of company each sub-domain applies to. MICRO companies (case 1) might be over-classified as IN_SCOPE for sub-domains that only apply to LARGE.

---

## Conclusion

The 5-spec Phase 1 LLM payload design is **mostly correct**, with **one critical gap** (P1B-LLM-02 missing company context) and a few minor gaps. The LLM is consistently given the AEGIS base system prompt + per-spec user prompt with case_id, lane_id, applicable_regs. The cross-regulation data (layer-0 sub-domains, pairs, HSOs) flows correctly to P1C-LLM-01 and P1B-LLM-01.

The P1B-LLM-02 gap is a **real bug** that explains the thin rationale output in real runs. It should be fixed in a follow-up contract (CORR-070 or similar).
